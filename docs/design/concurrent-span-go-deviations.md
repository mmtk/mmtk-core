# ConcurrentSpan: deviations from Go's code

Every place where our implementation differs from the Go code it ports. The port exists to evaluate Go's collector, so every difference has to be visible when results are reported. The rules are in [`concurrent-span-engineering.md`](concurrent-span-engineering.md) §3.

**Go reference:** `golang/go` master `2c3c1caad2` (2026-10-10). Paths are relative to `go/src/`.

**Scope.** Design-level deviations (barrier coverage, stack scanning, allocation stalls, reference processing, and so on) are summarised in [`go-gc-port.md`](go-gc-port.md) §11. This file records the code-level ones: places where a ported function, constant, table or state machine does something different from Go's code. When a code-level deviation changes the design, update §11 as well.

**Not deviations:** using MMTk's integration points (work packets, `Space`, options, side metadata), Rust idioms, and renaming to avoid "Go" in identifiers. Those are expected (engineering §3).

**Effect on the evaluation:** say which metrics could move and in which direction, or "none expected".

### SpanSpace (`SP` entries)

SpanSpace entries use the prefix `SP` (decision D36). The policy is in `src/policy/spanspace/`, the allocator in `src/util/alloc/span_allocator.rs`. Following the project lead's guidance, MMTk mechanisms are used where they are close, and Go's machinery is simplified where that does not change what defines Go's heap (size classes, span sizes, per-class spans, `sweepgen`-safe lazy and background sweeping, allocate-black, bitmap allocation). Each simplification is listed here so it can be revisited.

| ID | Go code | What Go does | What ConcurrentSpan does | Why | Effect on the evaluation | Our code | Design ref |
|---|---|---|---|---|---|---|---|
| SP1 | `runtime/mheap.go` (`gcBits`, `newMarkBits`, `newAllocBits`, `nextMarkBitArenaEpoch`); `runtime/mgcsweep.go:704` | Per-span `allocBits`/`gcmarkBits` sized to `nelems`, allocated from `gcBitsArena`s with a current/next/free epoch rotation. Sweep sets `allocBits = gcmarkBits` and takes fresh zeroed `gcmarkBits` from the next epoch | Fixed 1024-bit `alloc_bits` and `mark_bits` arrays inline in each span descriptor. Sweep copies the mark bits into the alloc bits and zeroes the mark bits | Much simpler; no arena lifetime management. Same invariant: marks are cleared per span by sweeping, never at Prepare | Descriptor memory is 256 B of bitmaps per span (about 3% of an 8 KiB span; Go uses `2*nelems/8` B). Sweep copies 16 words per span instead of swapping pointers. No effect on GC behaviour | `span.rs` (`Span::sweep_bits`) | §3.5, §5.3, §5.4 |
| SP2 | `runtime/mheap.go` (`mheap.grow`, `sysAlloc`, 64 MiB arenas), `runtime/mpagealloc.go` | Grows the heap by arenas, allocates pages with a radix tree of summaries over 4 MiB `pallocChunk`s, address-ordered first fit across the whole heap. Never unmaps; the scavenger returns free pages | Acquires 128 KiB page regions through `Space::acquire` (MMTk `FreeListPageResource`). A per-region page bitmap, address-ordered first fit by a linear scan over regions. Spans never cross a region boundary. A region whose pages are all free is returned to MMTk at once | Works with MMTk's heap accounting and with small heaps (MockVM tests use 1 MiB heaps; a 4 MiB unit could not be acquired). Linear scan is enough for phase 2 (design §5.3) | Tail fragmentation within a region (a 10-page span needs 10 contiguous pages in one 16-page region). Page allocation is O(regions). Returning regions early can cost re-acquiring them, but keeps MMTk's `FixedHeapSize` accounting meaningful. RSS is closer to live data than in Go without the scavenger | `pages.rs`, `global.rs` (`alloc_span`, `free_span`) | §5.3, §5.15 |
| SP3 | `runtime/mspanset.go`, `runtime/mcentral.go` | Lock-free `spanSet`s (FIFO: push at the tail, pop from the head) | One mutex per span class over `Vec`s (LIFO) | Simpler; acceptable at first (task instruction) | Contention when many threads refill the same class at once. Span reuse order is LIFO, not FIFO, which can change locality and which spans stay partially full | `central.rs` | §5.3 |
| SP4 | `runtime/mgcsweep.go` (`sweepLocker`, `sweep.active`, `isSweepDone`, `finishsweep_m`) | Counts active sweepers so that sweep completion is exact, and `finishsweep_m` waits for them | No active-sweeper count. `has_unswept()` looks at the central unswept sets; stale cached spans are swept by their allocators in mutator release; `prepare_initial_mark` sweeps any residue on the pause thread and asserts (debug) that all spans are swept | Simpler; in the STW phase there are no concurrent sweepers at Prepare | Before concurrent sweeping lands (phase 3), none. Afterwards, the plan must make sure sweep packets are finished or interrupted before InitialMark (design §5.5) | `global.rs` (`prepare_initial_mark`, `has_unswept`) | §5.5 |
| SP5 | `runtime/mgcsweep.go:920` (`deductSweepCredit`), `runtime/mheap.go` (`mheap.reclaim`) | Allocators sweep proportionally to allocation, and `mheap.alloc` sweeps (reclaims) pages before growing the heap | Not yet. Allocators sweep only the spans they take from the central sets; sweep packets sweep the rest | Phase 2 sweeps eagerly in the pause, so there is nothing for proportional sweeping to do yet | With concurrent sweeping, the heap may grow more between cycles than in Go until this is added | `global.rs` (`cache_span`) | §5.5 |
| SP6 | `runtime/mgcpacer.go` (`heapLive`), `runtime/mcache.go` (`refill`, `releaseAll`) | One global `heapLive`, updated at refill/uncache and by large allocations, reset to `bytesMarked` at mark termination | `SpanSpace::heap_live`, per space, with the same refill/uncache charging, reset to the space's own `bytes_marked` in `release_after_mark`. LOS bytes are not included | The plan combines spaces | The pacer must add LOS allocation to get Go's `heapLive` | `global.rs` (`cache_span`, `uncache_span`, `release_after_mark`) | §5.10 |
| SP7 | `runtime/mgcmark.go` (`gcw.bytesMarked`, flushed to `work.bytesMarked`) | Per-P counters, flushed | A striped atomic counter in the space (indexed by worker ordinal), read with `bytes_marked()`/`take_bytes_marked()` | No per-worker hook in the generic tracing path yet | None expected | `global.rs` (`add_bytes_marked`) | §5.4, §5.10 |
| SP8 | `runtime/malloc.go` (`mallocgc*`, `needzero`), `runtime/mheap.go` (`allocNeedsZero`) | Zeroes an object on allocation if its span `needzero`; tracks whether fresh pages are zero per arena (`zeroedBase`) | Same per-span `needzero` and per-object zeroing. Fresh page regions are zero because the space is created with `zeroed` (MMTk zeroes on acquire); pages of freed spans are tracked as dirty per region | MMTk owns mapping | An extra memset when a region is (re)acquired | `span_allocator.rs` (`zero_if_needed`), `pages.rs` | §5.3 |
| SP9 | `runtime/malloc.go` (size class from size) | Only `MinHeapAlign` (8 B) alignment, no offsets | An alignment above 8 B takes the next class whose object size is a multiple of it; an allocation offset pads within the cell, as other MMTk allocators do | MMTk's `alloc` API has `align` and `offset` | None for OpenJDK (8 B alignment, no offset) | `classes.rs` (`size_to_class_aligned`), `span_allocator.rs` | |
| SP10 | `runtime/mcache.go` (`prepareForSweep`), `runtime/mgc.go` (`gcMarkTermination`) | After mark termination each P flushes its mcache lazily (`prepareForSweep` on next use or via `forEachP`) | All mutators' span caches are flushed in the `ReleaseMutator` packets of the pause that ends marking | MMTk's mutator release is the natural place | A little more work in the pause (one uncache per cached span; stale spans are swept there) | `span_allocator.rs` (`release`) | §5.4 |
| SP11 | `runtime/mbitmap.go` (`findObject`) | Uses the pointer itself to find the span and object | Converts the reference to the object start (`ObjectModel::ref_to_object_start`) first | MMTk references may point inside the object (MockVM does) | None for OpenJDK (references are the object start) | `global.rs` (`object_start`) | §5.13 |
